# SmartPick

React parcel desk and ESP32 locker controller using the existing Neon database.

## Local development

Keep the frontend and API in separate folders and run them in separate terminals. The Vite dev server proxies `/api` requests to the backend, so browser code has no API key or hard-coded backend URL.

```sh
cd backend
cp .env.example .env
# Set DATABASE_URL, OPERATOR_LOGIN_PASSWORD, SESSION_SECRET, and ESP32_API_KEY.
npm ci
npm run dev
```

```sh
cd frontend
npm ci
npm run dev
```

Open `http://localhost:5173`. The API is at `http://localhost:5050`. Operator routes use an HttpOnly session cookie after sign-in. `OPERATOR_API_KEY` is supported only for trusted server-to-server callers; never put it in a `VITE_` variable.

## Deploy

`render.yaml` contains the configuration for deploying the API and built React frontend as one same-origin Render web service. You can enter the same settings when creating a Web Service manually. During setup, provide these values in Render:

If creating the service manually as a **Web Service**, leave Root Directory blank and use:

- Build Command: `npm ci --include=dev --prefix backend && npm ci --include=dev --prefix frontend && npm run build --prefix backend && npm run build --prefix frontend`
- Start Command: `npm --prefix backend start`
- Health Check Path: `/api/health/db`

- `DATABASE_URL`: the connection string for the existing Neon database.
- `OPERATOR_LOGIN_PASSWORD`: the parcel desk sign-in password.
- `ESP32_API_KEY`: a separate random device key; put the same value in the ESP32's private configuration.
- `SESSION_SECRET`: generated by the Blueprint.

Deploy, then check `https://<your-service>.onrender.com/api/health` and `/api/health/db`. The health check configured in `render.yaml` is `/api/health/db`. The backend connects to the already provisioned Neon database and does not create, reset, seed, or migrate tables. See [docs/database.md](docs/database.md). No database migration is needed for the scanner fix.

## ESP32

Configure the firmware with the deployed HTTPS base URL and the `ESP32_API_KEY` value. It makes outbound HTTPS requests, so no router port forwarding is needed. The device calls `/api/device/commands/next`, maps the returned slot and compartment numbers to the real hardware outputs, reports command results, and posts sensor-confirmed removal events. The barcode scanner in the parcel desk reads student ID barcodes to search by registration number; it does not scan parcel tracking labels. See [backend/ESP32_API.md](backend/ESP32_API.md) for request headers, payloads, event deduplication, and delivery limits.

Before wiring up the full flow, confirm the existing database contains a `hardware_devices` row and the correct slot and compartment records. The current backend associates commands with the first configured hardware device. Browser camera access requires HTTPS in deployment (or `localhost` during local development).

The current database and API support one configured ESP32 identity. Supporting multiple boards requires device-specific identity and credentials.

## Student ID scanner

The **Scan ID card** button reads the barcode on a student ID card and looks the student up by registration number.

- **Decoder:** [zxing-wasm](https://github.com/Sec-ant/zxing-wasm) (zxing-cpp compiled to WebAssembly) running in a Web Worker. The `.wasm` file is bundled into `frontend/dist/assets` and served from this app's own origin, so nothing loads from a CDN.
- **Formats:** Code 128, Code 39, Code 93, Codabar, ITF, EAN-13/8, UPC-A/E, DataBar, QR, PDF417, Data Matrix, Aztec. Code 39, Codabar and ITF have no mandatory check digit, so they need two identical reads before they are accepted.
- **Robustness:** each camera frame runs one of several passes (full frame, the on-screen guide region, ±10°/±20° rotations, 2× zoom), so tilted, distant, blurred and dim cards still decode.
- **Fallbacks:** upload a photo of the card, or type the number. Every path goes through the same validation (`frontend/src/scanner/identifier.ts`, mirrored in `backend/src/schemas.ts`) and the same lookup endpoint.
- **Matching:** exact match first. If there is none, a case-insensitive match is used only when it is unique, and an ambiguous match returns 409. Leading zeros are preserved; identifiers are never converted to numbers.
- **Diagnostics:** open *Scanner diagnostics* in the dialog to see the decoder status, camera, resolution, frames decoded and the last read (redacted). Set `localStorage['smartpick:scanner-debug']='1'` to log non-sensitive scanner events in a production build.
- Camera access requires HTTPS (or `localhost`).

`GET /api/students/:registrationNo/parcels` returns `{ registrationNo, parcels }`. It returns 404 for an unknown student, 409 for an ambiguous case-insensitive match and 400 for a malformed number.

## Testing

Tests never touch the production database. They need a disposable local PostgreSQL database, which the tests **reset** using `backend/test/schema.sql` (a test-only reconstruction of the schema):

```sh
createdb smartpick_test
export TEST_DATABASE_URL=postgresql://localhost/smartpick_test

npm --prefix backend test              # API + database integration tests
npm --prefix frontend run test:unit    # identifier/acceptor logic + real decoder on synthetic fixtures
npm run build && npm --prefix frontend run test:e2e   # Playwright: fake camera, real decoder, real API
```

For the E2E suite, run `npx playwright install chromium` once. Chromium's fake camera plays the synthetic card images in `frontend/tests/fixtures`; regenerate them with `make-barcodes.cjs` (needs `bwip-js`) and `make-cards.py` (needs Pillow and NumPy). All fixture names and numbers are fictional.

## Scripts

- `npm run dev` starts the Vite frontend.
- `npm run dev:backend` starts the API locally.
- `npm run build` builds the backend and frontend.
- `npm start` starts the built API, which serves the frontend when `frontend/dist` exists.
